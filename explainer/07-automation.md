# 07 — Automation

Three workflows in `.github/workflows/`.

## `daily.yml` — the pipeline

Runs at **02:30 UTC (08:00 IST)**, after most Indian companies have posted
overnight. Also runnable by hand via `workflow_dispatch`.

```
checkout (PAT)
   ↓
fetch postings          python -m pipeline.run
   ↓
commit raw data         git commit -m "data: pipeline run <date>"
   ↓
build + test            dbt build --fail-fast        ← the gate
   ↓
refresh README stats    python -m pipeline.stats
   ↓
push
   ↓
build dashboard         npm run sources && npm run build:strict
   ↓
deploy to Pages
   ↓
on failure: open or comment on a rolling issue
```

Order matters. The commit happens **before** the dbt build, so the raw data is
preserved even on a run whose transforms fail — you never lose a day's fetch to a
modelling bug. The deploy happens **last**, gated on everything above it.

`concurrency: daily-pipeline` prevents two runs writing the same partition at
once.

## The trap that kills most self-updating repos

This is the single most important thing in this file.

**GitHub disables scheduled workflows on public repositories after 60 days of no
repository activity — and commits made with the default `GITHUB_TOKEN` do not
count as activity.**

So the classic "git scraping" repo does this:

1. Sets up a daily cron that commits data with `GITHUB_TOKEN`
2. Runs beautifully for two months
3. Gets silently switched off
4. Shows a commit graph that stops dead, with no notification

For a project whose entire value proposition is *"a recruiter opening this in
October sees data from that morning"*, that is not a minor bug — it is total
failure, arriving exactly when it matters most.

The fix is one line:

```yaml
token: ${{ secrets.PIPELINE_PAT || secrets.GITHUB_TOKEN }}
```

Commits made with a personal access token count as user activity and reset the
clock. The fallback keeps the workflow functional for anyone who forks this
without setting the secret — they just inherit the 60-day limit.

## `ci.yml` — pull request checks

Three jobs:

| Job | Runs |
| --- | --- |
| `python` | ruff lint, ruff format check, **126 pytest tests** |
| `dbt` | `dbt build` against the committed sample dataset, then `verify_drift_detection.sh` |
| `dashboard` | dbt build, `npm run sources`, `npm run build:strict` |

**No test in CI touches the network.** Scraper tests run against saved API
responses in `tests/fixtures/`. CI must not depend on a third party's uptime, or
on some company happening to have a job open that day.

The sample dataset (`tests/sample_data/`, generated by
`scripts/make_sample_data.py`) has **8 days of history**, specifically so the
seven-day drift tests are actually armed in CI rather than dormant.

## `registry-check.yml` — weekly maintenance

Company boards go stale quietly. A dead slug contributes zero postings forever,
which looks identical to "they are not hiring".

Weekly, this validates every board in the registry and opens an issue listing any
that have died, with the exact command to re-prune. Rot is surfaced rather than
silently absorbed.

## Three deployment traps, learned the hard way

Every one of these produced a green local check and a broken deployment.

### `EVIDENCE_BASE_PATH` does not work

GitHub Pages serves a project site under `/<repo>`, so every asset URL needs that
prefix. The documented-looking environment variable was set correctly — verified
present in the run log — and Evidence 40 simply ignores it.

The result was the worst kind of failure: **HTTP 200, page loads, renders
completely unstyled**, because every `/_app/…` request 404s. A status check would
have called that a success.

The base path must come from the config file:

```yaml
deployment:
  basePath: /quantyx
```

### `evidence build` does not run `evidence sources`

It consumes parquet left by a previous `evidence sources`. A developer machine
has that cache sitting in `.evidence/`, so the build appears to work forever.

A fresh CI checkout has nothing, and every query fails with "table does not
exist". CI now runs `npm run sources` explicitly first.

### A bare `pytest` is not `python -m pytest`

The latter puts the working directory on `sys.path`; the former does not. Local
checks passed for days while CI failed on `ModuleNotFoundError: No module named
'pipeline'` — because the local command was not the CI command.

Fixed with `pythonpath = ["."]` in `pyproject.toml`, so both forms work.

**The pattern across all three:** the local check was not reproducing the CI
environment. The lasting fix was not any one of these patches — it was learning
to delete the caches and the local database and run the jobs exactly as CI
invokes them.
